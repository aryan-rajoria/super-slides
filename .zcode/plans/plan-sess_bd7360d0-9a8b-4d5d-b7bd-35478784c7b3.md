## Visual style (light + pixel/voxel)
- **Palette:** warm paper background `#F5F2EA`, ink text `#1B1D22`; accents echoing the dashboard's semantic colors darkened for light bg — blue `#2F6FED` (primary), green `#16A34A`, amber `#D97706`, red `#DC2626`, purple `#7C3AED`, cyan `#0891B2`.
- **Pixel devices:** hard offset shadows (no blur) on cards, chunky 3–4pt solid borders, stepped corner brackets, voxel-cube clusters (small grids of squares) as slide-corner motifs, square ■ bullets, pixel-divider strips of small colored squares. π logo drawn as pixel-block art in a rounded box.
- **Fonts:** slide titles rendered as pixel-font PNGs (download Press Start 2P or Silkscreen from Google Fonts, render via Python PIL or PowerShell System.Drawing; fall back to bold Verdana if unavailable). Event/tool/code identifiers in Consolas; body in Calibri. This guarantees the pixel look regardless of installed fonts.
- **Diagrams:** all visuals (data flow, entity relations, /research pipeline) drawn natively as shapes in the same pixel style — no dashboard screenshots (per the "native diagrams" default).

## Slide-by-slide outline

1. **Title** — "nano-super" pixel wordmark + π pixel logo. Subtitle: "Pi usage observation — a technical deep-dive." Tagline: "An agent that watches how you use your AI agent — and an AI that grades your prompting." Stat strip: v0.1.0 · ~3.6k LOC · 63 tests · 0 npm deps.
2. **The problem** — agent usage is a black box: sessions scattered per project; no cross-project view of prompts/tools/cost; failures hide inside exit-0 wrappers; prompting habits never get reviewed; drift noticed only in hindsight.
3. **What nano-super is** — two independent parts: `pi/` (package `nano-super-pi`: session monitor + `/research` command) and `dashboard/` (local analytics). Install = `pi install ./pi` + `node dashboard/server.js` — no npm install. One central log dir (`~/.pi/agent/logs`) for every project.
4. **What the monitor extension does** — hooks 7 pi lifecycle events → one JSONL line per event into `<sessionId>.jsonl`. Hot-path discipline: mkdir on first write only; single `appendFileSync` per event; every write in try/catch ("Monitoring must never break pi"); 200k-char truncation guard; `ephemeral-<rand8>` ids for `--no-session` runs.
5. **Data relations** — entity diagram: Session (JSONL, schemaVersion 1, 12 event types = 7 monitor + 5 `research_*`) ↔ Analysis (`<id>.analysis.json`, schemaVersion 2: outcome, 5 prompt classifications, drift root causes, hard/soft failures, phases, prompt coach with 8 habit tags) ↔ Digest (`.enrich/<id>.input.md`, 30k-char budget, event [N] == JSONL line N). Research runs link via `research_start.streamSessionIds` (A/B/C order) and `research_pdr.refineSessionId` to child sessions. Versioned on both sides.
6. **The dashboard pipeline** — flow diagram: JSONL logs → parse.js (mtime+size cache, 8 soft-failure regex families) → server.js (node:http stdlib, 5 endpoints, 127.0.0.1:3131) → SPA (no build step, vendored Chart.js, 15s auto-refresh). Watcher: scans every 5s, auto-enriches after 60s quiet (quit) / 10min (reload chains), one headless pi at a time.
7. **/research — six stages** — pipeline diagram: 1 scout (1 call → 3 candidate approaches) → 2 streams (3 parallel headless pi, read-only tools, 10-min cap) → 3 distill → 4 RTV (3 round-robin pairs × 3 votes) → 5 PDR (1 refine session) → 6 submit (brief injected as context).
8. **Paper → agent scale** — arXiv:2604.16529 "Scaling Test-Time Compute for Agentic Coding": N=16 rollouts → 3 streams (configurable 2–5); V=8 votes → 3 with one lens per vote (pragmatism/risk/effort) "so the V votes are not V copies of the same bias"; judges see distilled summaries, not trajectories (~2k tokens); survivor logic (≥2 streams required); tie-break ranking call resolves A>B>C>A cycles; PDR failure falls back to the winning brief.
9. **Decisions that were made** — gallery with one-line rationale each: zero-dependency stack ("Only Node.js required — no npm install"); versioned schemas on both files; feedback-loop guard (`PI_DASHBOARD_ENRICHMENT` no-op); monitoring-never-breaks-pi try/catch; 200k truncation; `stdin:"ignore"` (pi print mode hangs on an open pipe); enrichment runs through the pi harness, never direct API; submitted brief ends "trust the codebase and adapt"; soft failures flagged "suspected" until confirmed; central-dir install warning (double-logging hazard).
10. **Processing time & extra cost** — the honest numbers: monitor = one sync append per event (architectural guarantee — repo makes no latency benchmark claims); /research = 4 pi runs (3 parallel + 1 refine) + ~14 short LLM calls, typically 2–5 min (real fixture ran 6m25s with one stream timed out and dropped); enrichment = zai/glm-5.3-flash, 5-min timeout × 2 attempts, serialized; per-turn cost is tiny (real logged example: $0.000049/turn); parse cache means unchanged logs are read once per server run.
11. **Measurable benefits** — 9 KPI cards (sessions, tool calls, hard errors, suspected soft failures, correction steers, info steers, tokens, cost, analyzed N/M); 6 overview charts + drift/failure root-cause charts + prompt-coach habits; soft-failure forensics catches exit-0 failures `isError` misses; quantified waste from a real steering test: 3 wasted turns, one correction detour = 5 turns / 4 tool calls / 30s, drift root cause `prompt_ambiguity` with 6 cited evidence events; every AI finding cites event [N] traceable to a raw log line.
12. **Status & takeaways** — v0.1.0; zero-dependency discipline held end to end (server, SPA, tests); 63 tests in 4 suites; honest limits (single-user, localhost-bound, no latency benchmarks yet); meta takeaway: an agent observing your agent, analyzed by an agent — a closed loop with a guard so it can't feed itself.
