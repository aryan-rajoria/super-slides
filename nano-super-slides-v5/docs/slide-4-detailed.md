# Slide 4 — Translation Matrix, detailed edition

This is the expanded, self-contained version of [slide-4.md](slide-4.md) (which stays the
compact reference). Same matrix, same facts — but every cell is written for a reader who
has never used these tools: it explains what the harness is, what the surface looks like
inside it, and what exactly our registry has to do about it. All facts come from the
`agents-unified-registry/` corpus (verified 2026-10-16); versions studied: Claude Code
v2.1.302 · Codex rust-v0.163.0 · OpenCode 2.0.x · Pi 1.3.0.

## The four harnesses, in one minute

These are the four terminal coding agents ("harnesses") a published artifact should run on.

| Harness | What it is | Config style | Trust model |
|---|---|---|---|
| **Claude Code** | Anthropic's terminal coding agent, installed from npm (`@anthropic-ai/claude-code`). The richest extension surface of the four. | JSON files everywhere: `settings.json`, `~/.claude.json`, `.mcp.json` | Ask-to-approve tool permissions; admin "managed settings" cannot be overridden; npm-sourced plugins never run install scripts |
| **Codex** | OpenAI's open-source coding agent, written in Rust — one binary, one `~/.codex/config.toml` shared by the CLI, desktop app and IDE extension. | TOML everywhere (`config.toml`) | The strictest: three sandbox modes plus an approval policy; project-level files stay **inert until the user marks the project trusted** |
| **OpenCode** | Open-source TypeScript coding agent from Anomaly (formerly SST); the 2.0 rewrite runs on Node. Notably, it also reads Claude-format skill directories. | One `opencode.json` (JSONC) + `.opencode/` dirs | Per-tool allow / ask / deny permission maps in config; denies reading `.env*` by default |
| **Pi** | A deliberately minimal terminal coding agent by Mario Zechner (Earendil Works). Extensions written in TypeScript replace plugins, hooks and custom tools. | `~/.pi/agent/` dirs + npm packages | **No permission system and no sandbox at all** ("YOLO mode") — only a one-time project-trust prompt gating `.pi/` resources |

## The ten surfaces, in one minute

Each row of the matrix is one kind of artifact ("surface") a registry could distribute:

- **Skills** — folders of `SKILL.md` instructions the agent auto-loads when relevant.
- **Slash commands** — markdown files whose content becomes a `/name` prompt template.
- **Subagents** — helper agents with their own system prompt and tool scope, spawned for delegated work.
- **Hooks** — scripts fired automatically on lifecycle events (e.g. before a tool runs), which can veto actions.
- **Plugins** — bundles (skills + agents + hooks + MCP servers) installed from a marketplace.
- **MCP servers** — external tool servers (Model Context Protocol) the agent calls over stdio or HTTP.
- **LSP servers** — language servers giving the agent code-aware powers (diagnostics, go-to-definition).
- **Custom tools** — extra agent tools written in code (TypeScript or SDK), not files.
- **Status line** — a custom bottom-bar UI (script or theme).
- **Exec policy** — declarative rules for what the agent may do without asking (permissions, sandbox, network).

Verdicts (what our registry must do to serve an artifact to that harness):
**COPY-AS-IS** drop in unchanged · **TRANSLATE** the registry converts the format ·
**OVERLAY** a portable core plus harness-only extra fields · **NO SURFACE** the harness has
no native target — the record marks it unsupported.

## The matrix

| Surface | Claude Code | Codex | OpenCode | Pi |
|---|---|---|---|---|
| **Skills** | **OVERLAY** — Claude Code is spec-native here: skills are `SKILL.md` folders (with YAML frontmatter from the open Agent Skills spec) auto-loaded when relevant, living in `.claude/skills/` (project), `~/.claude/skills/` (user), enterprise directories or inside plugins. But Claude adds its own frontmatter extras — `when_to_use`, `argument-hint`, `context: fork`, per-skill `hooks` — which the registry must emit as a Claude-specific overlay on the portable core. Skill directories are unversioned file drops: no version tracking, no update mechanism (only plugins auto-update). | **OVERLAY** — Codex adopted the same Agent Skills spec, but skill folders live in `.agents/skills` (discovered by scanning from the working directory up to the repo root), `~/.agents/skills` (user) and `/etc/codex/skills` (admin). Codex-only behavior goes in an `agents/openai.yaml` sidecar next to the skill (interface settings, `policy.allow_implicit_invocation`, MCP dependencies) — that sidecar is the overlay. Enabling a skill path requires `[[skills.config]]` entries in `config.toml` **plus a restart**, and `$skill-installer` installs once — updating means re-copying the directory. | **OVERLAY** — OpenCode natively reads three skill dirs (walking up to the worktree root, later-wins): `.opencode/skills/` → `.agents/skills/` → `.claude/skills/`, so even Claude-format skills work. OpenCode-only behavior (auto-invocation, slash exposure) rides `metadata.opencode/*` keys inside the standard frontmatter. The big upside: the v2 HTTP **skills catalog** — point config `skills[]` at a URL serving `index.json` (`{"skills":[{name,version,files[]}]}`) and OpenCode caches each release under `~/.local/share/opencode/skills/<name>/<version>/`, so a version bump **is** the update. The most registry-ready surface of all four. | **COPY-AS-IS** — Pi reads the same agentskills.io spec folders from `~/.pi/agent/skills/` and `~/.agents/skills/` (plus `.pi/skills/`, which is trust-gated), so the registry just copies the directory. Two caveats: `~/.agents/skills` loads **un-gated** — ancestors of the working directory are scanned without the project-trust prompt that other `.pi/` resources require (a verified trust hole) — and there is no versioning at all unless the skill ships inside an npm pi-package. |
| **Slash commands** | **COPY-AS-IS** — Claude Code started this pattern: markdown files in `.claude/commands/` (project) or `~/.claude/commands/` (user) whose content becomes the prompt when the user types `/name`. It is now a **legacy** surface — commands were merged into skills — so the registry prefers emitting a skill instead. If emitted as a command anyway, subdirectories namespace it: `commands/db/migrate.md` → `/db:migrate`. | **COPY-AS-IS** — Codex calls these custom prompts: flat markdown files, user-scope only, in `~/.codex/prompts/`, invoked as `/prompts:<name>`, and a restart is required to pick them up. Officially **deprecated** — the docs steer you to skills. The registry can still emit the file verbatim, but should warn the installer. | **COPY-AS-IS** — a straight copy: `.opencode/commands/<name>.md` (or `~/.config/opencode/commands/`), where nested directories become the namespace (`a/b.md` → `/a/b`). Frontmatter extras — `agent`, `subtask`, `model` — are OpenCode-only, and v2 also accepts a `commands[]` config array. Templates support `$ARGUMENTS`, `$1…`, `` !`cmd` `` and `@file` substitutions. | **COPY-AS-IS** — prompt templates in `~/.pi/agent/prompts/` and `.pi/prompts/` (trust-gated), where the **filename is the command**: `review.md` becomes `/review`. Frontmatter carries `description` / `argument-hint`; arguments arrive as `$1..$n` and `${1:-default}`. Standalone files never update — only prompts shipped inside a pi-package do. |
| **Subagents** | **COPY-AS-IS** — Claude Code's format is the **canonical shape everyone else translates from**: markdown files with YAML frontmatter (`name`, `description`, `tools`, `model`, `memory`, `isolation: worktree`, …) where the body is the system prompt; locations are `.claude/agents/`, `~/.claude/agents/`, plugin `agents/`, or a `--agents` JSON flag. No versioning outside plugins. | **TRANSLATE** — subagents are **TOML** files here: `.codex/agents/*.toml` (project scope — inert until the project is trusted) or `~/.codex/agents/*.toml`. Required fields are `name`, `description`, `developer_instructions`; an agent cannot raise its parent's sandbox or approval level. Ships built-ins (`default`, `worker`, `explorer`). The registry must convert Claude's md frontmatter into this TOML. | **TRANSLATE** — OpenCode has its own markdown dialect: `.opencode/agents/<name>.md` where the filename is the id, frontmatter `description` (required), `mode: primary|subagent|all`, `model`, and permission maps. Built-ins: `build`, `plan`, `general`, `explore`, `scout`; v2 adds background subagents. The registry must translate the canonical fields into this dialect (and sniff v1/v2 config differences). | **NO SURFACE** — Pi has **no subagent capability in its core**. An official *example extension* (`packages/coding-agent/examples/extensions/subagent/`) adds markdown agents in `~/.pi/agent/agents/`, but whether it was ever promoted to core is UNVERIFIED. Emitting one means shipping executable extension code — review tier — so the record marks Pi unsupported. |
| **Hooks** | **COPY-AS-IS** — the richest hooks system: scripts fired on **30+ lifecycle events** (before/after tool use, session start, …) with five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`), JSON state on stdin, and exit-code semantics (exit 0 = proceed, exit 2 = block). Configured in `settings.json`, plugin `hooks/hooks.json`, or skill/agent frontmatter. Critical caveat: hooks from **all scopes merge** into one chain, so the registry must *merge* its entries into settings — never blind-drop a file over them. | **COPY-AS-IS** — Codex adopted a Claude-**compatible** hooks JSON (12 events, injecting `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` env vars) in `~/.codex/hooks.json` or project `.codex/hooks.json`. But the trust gates bite: the project layer stays inert until the project is trusted, and **plugin hooks are skipped until the user explicitly reviews them** (plugins with hooks are barred from the public directory entirely). | **TRANSLATE** — there is **no hooks file at all**; event reactions are TypeScript plugins in `.opencode/plugins/*.ts` hooking events like `tool.execute.before/after`, `permission.asked`, `session.*`, `lsp.*`, `tui.*`. The registry must **codegen a TS plugin** from the hook spec. Hazard: the v2 plugin rewrite is incompatible with v1 (event names and config keys changed), so emitters must sniff the version. | **TRANSLATE** — same story: extensions subscribe via `pi.on(event, fn)` (`session_start`, `tool_call`, `tool_result`, `turn_end`, …). The registry must codegen a TS extension. It runs **in-process with full OS access** — no sandbox — so it lands in the review tier. |
| **Plugins** | **TRANSLATE** — a plugin bundles skills, agents, hooks and MCP servers behind `.claude-plugin/plugin.json`. Distribution is **marketplaces**: git repos carrying `.claude-plugin/marketplace.json` that list plugins from 7 source kinds (relative / github / url / git-subdir / npm / archive / command); installs cache under `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. The official Anthropic marketplace is auto-added; npm-sourced installs **never run scripts** (the safe channel). The registry's bundle must be re-wrapped into this dual-manifest + git-repo structure, with the version living in manifest + marketplace entry + git sha. Plugins are also the *only* artifact Claude auto-updates (opt-in per marketplace). | **OVERLAY** — Codex is the only one of the four consuming the cross-vendor **Agent Plugins spec** (agent-plugins.org v1.0.0): a portable `plugin.json` at the root, plus a `.codex-plugin/plugin.json` overlay, `extensions.com.openai`, `.mcp.json`, `.app.json`. Marketplaces are `.agents/plugins/marketplace.json` (repo) or `~/.agents/plugins/marketplace.json` (personal), driven by `codex plugin marketplace add\|list\|upgrade\|remove`, the `/plugins` TUI, and `[plugins."name@mp"] enabled = true` in config. The **IDE extension supports none of this** — CLI/desktop only. `codex plugin marketplace upgrade` is Codex's only auto-updater. | **TRANSLATE** — plugins are TypeScript/JS modules (the `Plugin` type from `@opencode-ai/plugin`) in `.opencode/plugins/*.ts`, installed from **npm, git or a local path** via `opencode plugin add pkg@ver` (plus list/check/update/remove). There is **no official marketplace** — community aggregators (awesome-opencode, opencode.cafe, ocx) fill the gap. v1 plugins are incompatible with v2, so the registry publishes an npm adapter package per major. | **TRANSLATE** — packages are plain **npm packages** tagged with the keyword `pi-package` plus an optional `pi` key declaring globs (`{extensions[], skills[], prompts[], themes[]}`); the gallery is pi.dev/packages (**5,361 packages**, top package 1.6M downloads/mo). `pi install npm:\|git:\|path`, installs recorded in `~/.pi/agent/settings.json`, with `.pi/settings.json` acting as the project lockfile. npm IS Pi's registry — the registry should mirror **content-only** packages (no lifecycle scripts) to kill the postinstall-script attack surface. |
| **MCP servers** | **COPY-AS-IS** — MCP servers (external tool processes the agent calls over stdio, or remote ones over HTTP) are configured as `mcpServers` JSON entries — stdio `command/args/env` or `url`, `${VAR:-default}` expansion — via `claude mcp add -s local\|project\|user` / `add-json`, stored in `~/.claude.json` (user/local), `.mcp.json` at the project root (committed to the repo), or plugin `.mcp.json`. Caveats the registry must respect: the project `.mcp.json` needs **interactive approval** (`enableAllProjectMcpServers` to pre-trust), entries **replace rather than merge**, and admin `managedMcpServers` outranks every other scope. | **TRANSLATE** — Codex speaks MCP in **TOML**: `[mcp_servers.<id>]` sections in `config.toml` (command/args/env, or `url` with OAuth), managed by `codex mcp add <name> [--env K=V] -- <cmd> | --url`. Codex-only: **per-tool approval** (`default_tools_approval_mode`, `tools.<tool>.approval_mode`). A `.mcp.json` file exists only *inside plugins*. The registry must convert the JSON entry into TOML. | **TRANSLATE** — config entries in `opencode.json` (JSONC): `mcp.servers.<name>` in **v2** but `mcp.<name>` in **v1** — emitters must sniff which one the install has. Local servers take command/env, remote ones url/headers/OAuth; CLI is `opencode mcp add <n> --scope project\|user\|system`. Hazard: **global config overrides project** config. | **COPY-AS-IS** — the one true copy: Pi's `~/.pi/agent/mcp.json` / `.pi/mcp.json` (trust-gated) takes the Claude/Cursor `mcpServers` object **verbatim, per official docs** (`builtin:mcp` extension since 0.99.0). CLI `pi mcp add <name> [--local]`, OAuth via CIMD. Quirks: the SSE transport is rejected outright, and Pi's exposure model (`codemode`/`deferred`/`direct`/`hidden`) is Pi-only config the registry can optionally emit. |
| **LSP servers** | **TRANSLATE** — language servers exist **only inside plugins**: a root-level `.lsp.json` map (or a `lspServers` key in `plugin.json`), where every entry must declare `extensionToLanguage`. A bare `.lsp.json` cannot be dropped alone — the registry must wrap it in a plugin bundle. | **NO SURFACE** — LSP is absent from Codex's documentation entirely (as of rust-v0.163.0, 2026-10). The record marks it unsupported; nothing to install. | **NO SURFACE** — an `lsp` config key *exists*, but its schema is undocumented; there are just two plugin events (`lsp.client.diagnostics`, `lsp.updated`). Nothing a registry could reliably emit. | **NO SURFACE** — no LSP integration as of Pi 1.3.0. |
| **Custom tools** | **NO SURFACE** — custom tools exist only as in-process MCP servers **written in Agent SDK code** (`customTools` API): no filesystem path, no manifest, no version — nothing a registry could install or pin. | **NO SURFACE** — only `[tools]` / `[tool_suggest]` config toggles for built-ins (web search, image viewing). No registration surface. | **TRANSLATE** — tools are defined in TS plugins: `tool({ description, args: <Zod schema>, execute })`, and they can **override built-in tools**. The registry must codegen this from a declarative tool spec; `opencode plugin check` validates the result. | **TRANSLATE** — the richest tool API of the four — `pi.registerTool()` with a TypeBox schema, exposure control (`direct\|model-only\|codemode\|deferred\|hidden`), plus `registerCommand/Shortcut/Flag/Provider/McpServer/VirtualModel/ToolRenderer` — but it is still **codegen-to-TypeScript**, running in-process with full OS access (review tier). |
| **Status line** | **COPY-AS-IS** — a custom bottom-bar **script** fed JSON session state on stdin, wired through the `statusLine` settings key (any scope; the `/statusline` wizard configures it). No format to convert — dropping the script and setting the key *is* the install, and replacing the script is the update. | **NO SURFACE** — only `[tui]` notification config keys; no statusline surface at all. | **NO SURFACE** — no statusline is documented; **themes** (`.opencode/themes/<name>.json`, selected via `/themes`) are the closest JSON drop the registry can serve. | **OVERLAY** — theming is strict JSON: `~/.pi/agent/themes/<name>.json` where the theme's `name` field **must equal the filename**, on a strict schema; deeper TUI customization requires extension code (`ctx.ui.*`, review tier). A portable look needs a Pi-specific overlay. |
| **Exec policy** | **OVERLAY** — nothing to install: the record's declared required-permissions must become **allow-rules** in `settings.json` (`permissions.allow/deny`). Guards the registry must know: `auto`/`bypassPermissions` modes **cannot be set from project/local settings**, admin `managed-settings.json` keys (`disableSkillShellExecution`, `allowManagedPermissionRulesOnly`, …) are unoverridable, and `--accept-command <sha256>` pins approved commands. | **COPY-AS-IS** — the **richest policy surface of the four**: `sandbox_mode` (`read-only` / `workspace-write` / `danger-full-access`) with `[sandbox_workspace_write]` (`writable_roots`, `network_access`), `approval_policy` (including granular `skill_approval`), `[permissions.<name>]` profiles, **Starlark `.rules` files** (`prefix_rule(...)`, checked by `codex execpolicy check`), an admin `requirements.toml` layer, and Windows sandbox modes. `.rules` files drop in verbatim — but the record must declare its sandbox + approval needs for anything else to derive. | **OVERLAY** — permissions are config arrays: `permissions[] {action, resource, effect}` in v2 (v1 used per-tool allow/ask/deny maps, last-match-wins). Defaults already deny reading `.env*` and ask on `doom_loop`/external directories; `--auto` approves everything non-denied. Two quirks: **global config overrides project**, and org policies can be pushed via a `.well-known/opencode` endpoint. | **NO SURFACE** — Pi has **no permission system and no sandbox** ("YOLO mode"); the only gates are the project-trust prompt (`defaultProjectTrust: ask\|always\|never`) and the `codemode` QuickJS sandbox for *model-written* JS. Nothing declarative to emit — the record carries trust/risk metadata so the user can judge before installing. |

## Auto-update — who can update what

The short version: **only bundles update themselves**. A plugin/package marketplace can
refresh what it installed, but a standalone skill, command, subagent, hook or MCP entry is
a manual file drop in every one of these harnesses. Since nothing pins or updates those
files, that job falls on our registry's lockfile (`agentreg.lock` — urn → version →
sha256 → per-harness targets), which no harness ships today.

| Harness | Self-updates | Mechanism | Everything else |
|---|---|---|---|
| Claude Code | plugins (opt-in per marketplace, since v2.0.70) | marketplace refresh | skills · commands · agents · hooks · MCP: manual drops/edits |
| Codex | plugins only | `codex plugin marketplace upgrade` | skills · prompts · agents · hooks · MCP · policy: manual edits |
| OpenCode | skills (per-version catalog cache) · plugins (+ hooks/tools codegen'd as plugins) | version bump in `index.json` · `opencode plugin update` | commands · agents · MCP · policy: manual edits |
| Pi | anything shipped in an npm pi-package (extensions · skills · prompts · themes) | `pi update [--extensions]` | standalone skill/prompt/theme drops · MCP: manual |

## The frictions that shape the registry

1. **One format is not enough.** MCP alone needs JSON (Claude/OpenCode/Pi) *and* TOML
   (Codex); agents need md (Claude/OpenCode/Pi-example) *and* TOML (Codex). The emitter,
   not the publisher, owns the conversion.
2. **Hooks and custom tools are codegen surfaces.** OpenCode and Pi have no hooks file —
   both need generated TS. Claude hides tools in SDK code, Codex has neither.
3. **Plugins are per-harness re-wraps.** Same bundle becomes a `.claude-plugin/`
   marketplace repo, a `plugin.json` + `.codex-plugin/` overlay, an npm TS package
   (OpenCode), and an npm `pi-package` (Pi).
4. **Trust gating differs in kind.** Codex gates project layers + plugin hooks behind
   trust/review; OpenCode lets global config override project; Pi gates `.pi/` but loads
   `~/.agents/skills` un-gated; Claude has unoverridable managed keys.
5. **`NO SURFACE` is real data.** LSP (Codex, OpenCode, Pi), statusline (Codex,
   OpenCode), custom tools (Claude, Codex), subagents (Pi) — the record must say
   `supported = false`, never silently break.
